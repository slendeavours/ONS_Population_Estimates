# S19 month keys and first editions load

Status: done 2026-10-08. Follows the S19 PIP editions design
(`docs/superpowers/specs/2026-10-08-s19-pip-editions-design.md` in the parent repository) and works
like the [S8b first load](2026-10-08-s8b-editions-first-load.md). Applies `docs/RULES.md` rule 8
(period keys).

## The relabel

S19 is the DWP Stat-Xplore count of Personal Independence Payment cases with entitlement (total, and
enhanced daily living award), one row per English authority and month, in `la_pip_claimants`.

Its months were stored as text labels (`Apr-26`, `Jul-26`). A label sorts by its first letter, so
`MAX(month)`, which Workflow 1 uses to pick the latest month, would pick the wrong month once a third
label arrived (`Jul-26` sorts after `Aug-26`). Rule 8: periods are stored as sortable `yyyymm` keys,
and a display label is made when needed and never stored as the key.

`python scripts/s19_pip_editions.py migrate-months --commit` relabelled the live table in one
transaction (table locked, checked before commit). Only the `month` column changed. Values and
`loaded_at` were left as they were.

| Label (before) | Key (after) | Rows |
| --- | --- | --- |
| `Apr-26` | `202604` | 296 |
| `Jul-26` | `202607` | 296 |

The mapping is `Mon-yy` to `20yy` + the two-digit month number. To reverse it, map each key back with
the same table (`202604` to `Apr-26`, `202607` to `Jul-26`). Months 202605 and 202606 did not exist as
labels: they were first loaded after the relabel and have no label form to go back to. Running
`migrate-months` again does nothing; it reports that every month is already a key.

The latest month's 296 per-area values were identical before and after. A SHA-256 hash of
(area, total, enhanced) over all 592 rows was the same before and after the relabel, and the same
again at the end of the load. A hash that included the month text changed, as it should. The view
`v_la_pip_rates` returned 592 rows before and after and now shows `yyyymm` months.

## The editions table

New append-only table `la_pip_claimants_editions` (update, delete and truncate are blocked by
trigger; the month must be six digits), key `(lad24cd, month, edition)`. It holds every release of
every month. The live table holds the latest edition of each month.

`sync-new --expected-authorities 296 --commit` recorded edition 1 'as loaded' for the two held months
(592 rows; the published date is the 1 October 2026 load date). Nothing was fetched for that step.

## What the first recheck found

`load --recheck-all` fetched all four months from the Stat-Xplore API on 2026-10-08. The API offered
201901 to 202607 (91 months). The latest month is still 202607.

| Month | Result | Edition | Rows | Total | Enhanced daily living |
| --- | --- | --- | --- | --- | --- |
| 202604 | unchanged (0 areas differ) | 1 | 296 | 3,708,965 | 1,944,596 |
| 202605 | new | 1 | 296 | 3,728,716 | 1,955,921 |

| 202607 | unchanged (0 areas differ) | 1 | 296 | 3,788,643 | 1,985,494 |

**April and July 2026 were not revised by DWP.** Every cell matched the 1 October load. The source
registry's note, tested once and negative, holds after a second test. Nothing beyond edition 1 was
stored, and `refresh-latest` was not needed.

May and June 2026 filled the gap after the earliest held month. Each was stored as edition 1, and its
296 live rows went in in the same transaction. No month had NULLs, zeros or negative values. The
months before April 2026 were not loaded: the loader never goes back before the earliest held month.

The live table now holds 1,184 rows (four months x 296 authorities), and `v_la_pip_rates` returns
1,184 rows. `status` says OK. `python scripts/s19_pip_editions_verify.py` passed all 19 gates (exit 0)
with the real-table gates evaluated.

## Table comment

The old `COMMENT ON TABLE la_pip_claimants` said 'Month loaded: Jul-26', with coverage and
confidence for that single load. It was replaced (metadata only) with a neutral comment. The new one
says the periods are `yyyymm` keys, that the table holds the latest edition of each month and that
`la_pip_claimants_editions` holds every release. It keeps the sentence that the absence of a row
means no published data for that authority, not zero.

## The monthly check

From `ONS_Population_Estimates`:

1. `python scripts/s19_pip_editions.py load` previews. It fetches every month the API offers that is
   not held and is later than the earliest held month, plus the latest six held months as a revision
   check, and says for each month whether it is new, unchanged or revised. Nothing is written.
   `--recheck-all` rechecks every held month. API calls are throttled, so four months take about ten
   minutes.
2. Read the preview. The loader refuses a short month (fewer than 296 authorities, or a measure
   missing). Before you commit, stop and look if NULLs appear where there were numbers, if any value
   is negative, or if a large revision affects many authorities.
3. `load --commit` stores new months as edition 1 and inserts their live rows in the same
   transaction. A revised month is stored as the next edition and reaches live only through step 4.
4. `refresh-latest` previews the live rows that would change; then run it with `--commit`.
5. `status` should say OK, and `python scripts/s19_pip_editions_verify.py` should pass all 19 gates.

The Stat-Xplore key is read from the environment and is never printed or stored.
