# Historical scripts

These scripts patched or ran Workflow 1 (W1) inside n8n, before W1 moved into the repo (`sql/w1` and `scripts/w1_run.py`). They are kept for history only and are not used; their imports may no longer resolve.

`s8b_hb_accom_type_build.py` is the original S8b (Stat-Xplore Housing Benefit caseload by accommodation type) loader. It upserted the live table in place, so a DWP revision overwrote what was held. It was replaced on 2026-10-08 by `scripts/s8b_hb_editions.py`, which keeps every revision as a numbered edition. It is kept for history only and cannot run from here: it imports the shared `statxplore_client`, which it can no longer find from the `historical` folder.

`s15_hpi_build.py` is the original S15 (Land Registry UK HPI) loader. It inserted new months only (`ON CONFLICT DO NOTHING`) and discarded revisions of months already held, and it took its edition name from a constant and its files from a hand-off folder under the temp directory. On 2026-10-09 it was replaced by `scripts/s15_hpi_editions.py`, which keeps every revision as a numbered edition. **Do not run it**: it now stops at once with a RETIRED message.

`s18_pipr_fetch.py`, `s18_pipr_transform.py`, `s18_pipr_load.py` and `s18_pipr_verify.py` are the original S18 (ONS Price Index of Private Rents) pipeline. It upserted rows in place (`ON CONFLICT DO UPDATE`) from 2026-07-12 until commit ab14ef9 (2026-10-01), so the 22 July and 19 August 2026 loads overwrote held rows, and after that inserted new rows only and ignored revisions of rows already held (`ON CONFLICT DO NOTHING`). It took its edition from a command-line argument. On 2026-10-09 it was replaced by `scripts/s18_pipr_editions.py`, which keeps every revision as a numbered edition. **Do not run any of the four**: each stops at once with a RETIRED message. (`s18_pipr_inspect.py` stays in `scripts/` as a read-only workbook inspector.)

`s9a_drd_build.py`, `s9b_crfd_build.py`, `verify_load_drd.py` and `verify_load_crfd.py` are the original S9a (NHS England Discharge Ready Date) and S9b (MHSDS measure MHS26) loaders. The two build scripts upserted rows in place (`INSERT ... ON CONFLICT DO UPDATE`, setting `loaded_at`), so loading a republished file overwrote held rows, though, as far as `loaded_at` and the files show, no held month was reloaded from a different file after its first load (the one exception: the held S9b Barnsley/Sheffield rows were re-keyed in place on 2026-08-14 and 2026-10-01, which left `loaded_at` unchanged). The S9b build took the file URL and period on the command line and had no Final filter of its own; the year-end Final files were kept out by the discovery in `verify_load_crfd.py` and the n8n-era load, not by the build. The two `verify_load_*` scripts loaded June 2026 on 2026-08-20 (S9a from the CSV form of the file) with the same upsert. On 2026-10-09 they were replaced by `scripts/s9a_drd_editions.py` and `scripts/s9b_crfd_editions.py`, which keep every revision as a numbered edition. **Do not run any of the four**: each stops at once with a RETIRED message. (The files they were checked against stay in `scripts/verify/src/` as evidence.)

`s19_pip_build.py` is the original S19 (Stat-Xplore PIP claimants) loader. It wrote text month labels such as `Apr-26` and upserted the live table in place. On 2026-10-08 the live months were relabelled to `yyyymm` keys (`Apr-26` is now `202604`, `Jul-26` is `202607`) and the loader was replaced by `scripts/s19_pip_editions.py`. **Do not run it**: it would write labels again and undo the relabel. The saved queries `scripts/s19_query_total.json` and `scripts/s19_query_enhanced_dl.json` were written by this old loader; they are kept but nothing writes them now.

`s11_cqc_fetch.py`, `s11_cqc_process.py`, `s11_cqc_map.py`, `s11_cqc_load.py` and `s11_cqc_verify.py` are the original S11 (CQC Care directory with filters) pipeline. The load step upserted with `INSERT ... ON CONFLICT (location_id) DO UPDATE`, setting `loaded_at`, so each new file replaced the row of every location it contained (locations that dropped out of a file kept their earlier values); the July and August 2026 snapshots were rebuilt from the files on 2026-10-09, and the residue rows (128 July, 108 August) also remain in `cqc_locations_legacy`. The map step wrote `cqc_unresolved_locations` on every run, in place, with no preview; the fetch step overwrote a same-named download and took the file date from the file name; the July 2026 file was loaded twice on 2026-07-12. On 2026-10-09 they were replaced by `scripts/s11_cqc_editions.py`, which keeps each file as a dated snapshot. **Do not run any of the five**: each stops at once with a RETIRED message.

`s4_rebuild_care_leavers.py` (formerly `scripts/verify/rebuild_care_leavers.py`) is the 2026-08-20 rebuild of the S4 (DfE care leaver accommodation) table. It upserted with `INSERT ... ON CONFLICT (lad24cd, reporting_year, age_group) DO UPDATE`, setting `loaded_at`, so it overwrote the 17-21 rows already held; it was run at least twice on 2026-08-20. It added suppressed cells as 0 (`v or 0`), resolved codes through every `la_code_lookup` row (which recoded Bournemouth and Poole 2019 to BCP, where the held 2019 BCP row was all zeros), and dropped and recreated the backup table `care_leaver_accommodation_bak_20260820` on every run, so that table is the state after the first run and not the earlier state. The n8n S4 workflow before it (2026-03-31, loaded twice) had the same kind of upsert, dropped every county council through an inner join on `la_code_lookup`, and kept only the last age row for 22-25. On 2026-10-09 the S4 load was replaced by `scripts/s4_care_leaver_editions.py`, which keeps every release's figures as numbered editions. **Do not run it**: it stops at once with a RETIRED message. (The files it read stay in `scripts/verify/src/` as evidence.)

`s22_ctb_discover.py`, `s22_ctb_empties_build.py`, `s22_run.py` and `s22_verify.py` are the original S22 (MHCLG Council Taxbase and Live Table 615) build, committed together on 2026-08-13 and run once, that day (run-log id 83). The build step upserted all three tables with `INSERT ... ON CONFLICT DO UPDATE`, setting `loaded_at`, so a second run would have overwritten the held rows; nothing was overwritten in practice, because no earlier S22 load existed and the held rows carry one `loaded_at`. It wrote when run (no preview, no `--commit`), kept a same-named raw download whatever its content, and took the release from the landing page rather than the file. Its total of the unoccupied exemption classes would have counted a suppressed class as 0; it never did on the 2025 file. `s22_verify.py` also wrote a run-log row each time it ran. On 2026-10-09 they were replaced by `scripts/s22_ctb_editions.py`, which keeps every file's statement about every year as a numbered edition. **Do not run any of the four**: each stops at once with a RETIRED message.
